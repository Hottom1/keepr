# Decisions

Architectural choices made while turning Keepr from a Claude.ai artifact into a deployed app, and why.

## Phase 1 — Repo scaffold

**Stack: Vite + React 19 + Tailwind v4, installed directly rather than via `npm create vite`.**
The directory already had `keepr.jsx` and a `.claude/` folder in it, so the interactive scaffolder wasn't a clean fit. Built the project by hand instead: `npm init -y`, then installed `react`, `react-dom`, `lucide-react`, `recharts` as dependencies and `vite`, `@vitejs/plugin-react`, `tailwindcss`, `@tailwindcss/vite` as dev dependencies.

**Tailwind v4 via the `@tailwindcss/vite` plugin, no `tailwind.config.js`.**
v4 doesn't need a JS config file or PostCSS setup for a project with no custom theme — `@import "tailwindcss";` in `src/index.css` plus the Vite plugin is enough. Keepr's colours are all applied via inline `style` props (not Tailwind color classes), so there's no theme to extend yet. If that changes, a `@theme` block in the CSS file is the v4-native place to add it, not a config file.

**`keepr.jsx` ported to `src/App.jsx` verbatim.**
No restructuring into smaller component files yet — the brief for this phase was to confirm the port works before adding infrastructure, not to refactor. Splitting `App.jsx` into per-feature files is worth doing before Phase 2 gets underway, since the Supabase swap will touch every `updateAndSave` call site.

**`window.storage` shimmed in-memory (`src/lib/mockStorage.js`), not `localStorage`.**
The original code calls `window.storage.get(key, isPublic)` / `.set(key, value, isPublic)`, an API that only exists inside the Claude.ai artifact sandbox. Shimming that exact interface with an in-memory `Map` meant zero edits to the ported component for Phase 1, and keeps the shim obviously temporary — it forgets everything on reload, which is intentional so Phase 2's Supabase swap is the first real persistence this app gets, not a second temporary one (localStorage) that would need unwinding later.

**Kip's direct Anthropic API call left untouched for now.**
`KipChat` still `fetch`es `https://api.anthropic.com/v1/messages` client-side with no `Authorization` header — that only worked inside Claude.ai's sandbox, which intercepted the request. It will fail in this app (no key, likely CORS) until Phase 4 replaces it with a call to a Netlify Function proxy. Left as-is deliberately rather than stubbed, so it fails loudly and visibly rather than silently, as a marker of exactly what Phase 4 needs to fix.

## Phase 2 — Supabase: auth + data

**Data model: single `user_data` JSONB row per user, not normalized tables.**
Presented both options; user chose the blob. One table, `public.user_data(user_id uuid primary key, data jsonb, updated_at)`, with three RLS policies (select/insert/update, all `auth.uid() = user_id`). Migration lives in `supabase/migrations/0001_user_data.sql` — written for the user to run in the Supabase SQL Editor, since there's no CLI link or DB credential in this environment. The blob shape mirrors exactly what was already in React state (`customExercises`, `plans`, `season`, `profile`, `kipMessages`, `matches`), so `src/lib/storage.js`'s `loadUserData`/`saveUserData` are near drop-in replacements for the old `window.storage.get/set` calls in `App.jsx` — one `select`, one `upsert`, both scoped to `auth.uid()` server-side by RLS rather than trusted client-side. Escape hatch if it's ever needed: peel `matches`/`shots` into real tables later without touching the rest, rather than normalizing everything.

**No service-role key anywhere in this app.**
`src/lib/supabaseClient.js` only ever holds the `anon` public key (`VITE_SUPABASE_ANON_KEY`, from `.env.local`, gitignored). All access control is enforced by Postgres RLS using the caller's JWT, not by trusting the client. If a future serverless function genuinely needs to bypass RLS, that's a separate, explicit decision — not a default.

**`TempAuthGate` — deliberate, temporary scope overlap with Phase 3.**
Testing the Supabase read/write wiring requires *some* signed-in session, but building real sign-up/login/forgot-password/logout is Phase 3's job. Rather than block Phase 2 on Phase 3, or fake a session, added `src/TempAuthGate.jsx`: a bare email/password `signInWithPassword` form with no sign-up, wrapping `<App/>` in `main.jsx`. It's flagged in its own header comment as throwaway. Phase 3 replaces it outright rather than extending it — it's a verification tool, not a foundation.

## Phase 3 — Login/auth UI

**The app now lives at `/app`, not `/`.**
Added `react-router-dom` and moved the protected `GKTrainerApp` behind `/app`, with `/login`, `/signup`, `/forgot-password`, `/reset-password` as public routes and a catch-all that redirects to `/app`. This is ahead of need — Phase 5 hasn't happened yet — but it means the marketing landing page can claim `/` later without a breaking route change to anything built now. Flagging this since it's a structural call made before the page it's really for exists; easy to change if a different structure is preferred once Phase 5 is in view.

**`react-router-dom` pinned to the latest release (7.18.2), not downgraded.**
`npm audit` flagged a high-severity advisory in the 7.12–8.2 range, but it's specific to React Router's RSC (React Server Components) mode, which this app never uses — it's a plain Vite SPA with a client-side `<BrowserRouter>`, no server data loading or server actions. Tried pinning to 7.11.0 to dodge that advisory, but that range carries a much larger set of advisories that *do* apply to plain client-side routing (open redirects in `<Link>`/`useNavigate`, XSS in `ScrollRestoration`), all fixed by 7.17.0+. Latest is the safer choice for how this app actually uses the library.

**`TempAuthGate.jsx` deleted, not folded into the new auth flow.**
Real auth lives in `src/auth/`: `AuthProvider` (session context + `signOut`), `ProtectedRoute` (redirects to `/login`, preserves the originally-requested path via router state), and `LoginPage`/`SignupPage`/`ForgotPasswordPage`/`ResetPasswordPage`, all sharing an `AuthLayout` shell styled to match the rest of the app (same navy/teal/paper tokens, same input styling pattern as the existing `Modal` component's `.input` class).

**Sign-up handles both of Supabase's confirmation modes.**
`supabase.auth.signUp()` returns a session immediately if email confirmation is off in the project's Auth settings, or `session: null` if it's on. `SignupPage` checks for a session and either logs the user straight in or shows a "check your email" screen — it doesn't assume which mode the project is in.

**Password reset needs a Supabase-side redirect URL allowlisted — can't be done from code.**
`ForgotPasswordPage` sends users to `${origin}/reset-password`. Supabase rejects redirect URLs that aren't on the project's allowlist (Authentication → URL Configuration → Redirect URLs). `http://localhost:5173/**` needs adding now, and the production domain once Phase 6 deploys — this is a dashboard setting, not something a migration or client code can set.

**Sign-out lives in `App.jsx`'s `TopBar`, not a new component.**
One `useAuth().signOut` call behind a small icon button next to the existing "Keeper training" label — didn't introduce a new header or settings surface for a single action.

**Email-link flows (password reset, sign-up confirmation) verified as working server-side, but not click-tested end-to-end locally.**
The dev server this session runs against lives inside this sandboxed session, not the user's own machine — an email opened on their real device can't reach its `localhost:5173`. Confirmed the reset-request itself completes without error server-side (Supabase only returns the "check your email" success state when the API call succeeds), so the code path is sound; the actual link-click flow gets verified once Phase 6 deploys to a real, publicly-reachable domain. Documented here rather than treated as done, since it's genuinely unverified past that point.

## Phase 4 — Kip proxy

**Netlify Functions, per the brief's own Technical Requirements section — not re-litigated as a choice.**
The brief's build-order text says "your call" between a Netlify Function and a Supabase Edge Function, but the Technical Requirements section lower down already commits to "Netlify (Functions for the Kip proxy)." Went with that rather than treating it as open: Phase 6 already deploys via Netlify, so colocating the function there means one deploy target and one place secrets live, instead of splitting the backend across two platforms.

**`netlify/functions/kip-chat.js` verifies the caller's Supabase session before calling Anthropic.**
This endpoint is public once deployed — anything short of checking auth would let anyone with the URL burn the Anthropic budget, key or no key. The client sends its Supabase access token as a bearer header; the function verifies it via `supabase.auth.getUser(token)` (using the anon key, same as the client) before forwarding anything to Anthropic. `KipChat`'s `sendMessage` now fetches `/.netlify/functions/kip-chat` with that token instead of calling Anthropic directly — the API key itself never reaches the browser.

**Model id corrected from `claude-sonnet-4-6` to `claude-sonnet-5` while wiring this up.**
Flagged back in the Phase 1 summary as a model id I didn't recognize and hadn't verified. Now that this call is actually being made for real (rather than intercepted by the Claude.ai sandbox, which didn't care what string was in the `model` field), it needed to be a real, current model id — `claude-sonnet-5` is correct per current model documentation. Worth a second look if this stops working after a future model deprecation.

**`netlify-cli` added as a devDependency so functions are testable locally.**
Plain `vite dev` only serves the frontend — it doesn't know how to run `netlify/functions/*`. Added a `dev:netlify` script (`netlify dev`) and a `netlify.toml` `[dev]` block that proxies Vite on 5173 through Netlify's dev server on 8888, so both the app and the function are reachable from one place during local testing.

**Server-side secrets live in root `.env`, separate from the client-facing `.env.local`.**
`.env.local` keeps the `VITE_`-prefixed values Vite exposes to the browser bundle (Supabase URL/anon key). `.env` holds `SUPABASE_URL`, `SUPABASE_ANON_KEY` (unprefixed duplicates, read server-side by the function — same public-by-design values, just without the `VITE_` prefix so there's no ambiguity about which context reads which var) and `ANTHROPIC_API_KEY`, which never appears in `.env.local` or any client-reachable file. Both files are gitignored; `ANTHROPIC_API_KEY` still needs setting directly in Netlify's dashboard env vars for the deployed site in Phase 6, since `.env` never gets committed or uploaded.

**Accepted, monitored `npm audit` finding: `sharp`/libvips CVEs via `netlify-cli`'s optional image-transform tooling.**
Already on `netlify-cli`'s latest release (27.0.1); the vulnerable `sharp` version is pulled in transitively by `@netlify/images`, a dev-only image-proxy feature this project doesn't use. It's a devDependency that never ships to production or reaches an end user, and there's no newer release yet that resolves it. Not forcing a downgrade over it — will revisit if Netlify ships a patched release.

## Phase 5 — Marketing landing page

**`/` now renders the landing page; the catch-all redirects there instead of `/app`.**
This is the payoff of the Phase 3 call to put the protected app at `/app` ahead of need. No route changes needed to existing pages — `/`, previously unclaimed, now renders `src/marketing/LandingPage.jsx`; everything else (`/login`, `/app`, etc.) is untouched.

**Copy is grounded in what's actually built, not generic SaaS language — this is a first draft for review, not a final.** Per the brief's explicit ask. Four feature sections map directly to real functionality (Library, Builder, Stats, Kip), described in terms of what they actually do rather than benefit-speak. Flagging specifically for your review:
- The headline ("Built for the goal. Not the outfield.") and positioning line ("Keepr starts from the goal line.") are a first pass — there are more literal alternatives (e.g. leading with "handball goalkeeper training app") if this reads as too clever for the audience.
- No exact drill count is quoted in the library section (deliberately — the real number lives in `DEFAULT_EXERCISES` in `App.jsx`, and hardcoding it here risked drifting out of sync). Said "add your own alongside the built-in set" instead. If you want a hard number quoted, it needs pulling from that array, not typed by hand.
- Beach handball is given equal billing to indoor throughout, on the assumption it's not an afterthought market for you — worth confirming, since it's the smaller of the two disciplines in most regions.

**Hero visual is a stylised, illustrative goal-grid (real component logic, fake numbers), not a real product screenshot.** Built with the same save%-color-banding logic as the actual in-app `GoalGrid` (`≥60% teal / 40–59% amber / <40% red`), so it's an honest representation of what the feature looks like, not a mockup with invented UI. Didn't use an actual screenshot of the running app — happy to swap in a real one once there's a Stats page with enough logged data to look good, rather than screenshotting the mostly-empty dev account.

**Session-aware CTA, no forced redirects.** The primary button and header link read "Start training free" / "Log in" when signed out, "Go to your training" / "Open app" when signed in — using the same `useAuth()` hook as the rest of the app. Deliberately did *not* force-redirect a signed-in user away from `/` — someone might land there from a shared link and still want to see the marketing page.

**Privacy Policy and Terms of Service added at `/privacy` and `/terms`, linked from the landing page and legal-page footers.** Content is grounded in the actual data flows built in this project (Supabase for auth/storage under RLS, Anthropic via the server-side proxy for Kip, Netlify for hosting) rather than generic boilerplate — no claims about things that aren't true (no ad tracking, no data sales, because there are none). Flagging clearly: **this isn't legal advice and hasn't been reviewed by a lawyer.** It's a solid, honest starting draft; before a real public launch you should have someone qualified review it, particularly the liability/disclaimer language in the Terms given this app gives physical training advice (diving, sliding) with real injury risk. Also: the contact email used throughout is a placeholder (`hello@keepr.coach`) — that inbox doesn't exist yet and needs setting up (or forwarding) once the domain is live.

## Phase 6 — Netlify deploy

**Site created and deployed via Netlify CLI with a personal access token, not `netlify login`.** The user provided a token generated from their own Netlify account (User settings → Applications) rather than completing the interactive browser OAuth flow in this environment. Used it as `NETLIFY_AUTH_TOKEN` for CLI calls only within this session — not written to any file in the repo. Site name `keepr-app` was taken, Netlify auto-suffixed it to `keepr-app-482` (`keepr-app-482.netlify.app`); worth renaming once the custom domain is attached, since the auto-suffixed name will otherwise stick around as the default Netlify subdomain.

**All five environment variables set via `netlify env:set`, not the dashboard.** `SUPABASE_URL`, `SUPABASE_ANON_KEY`, `ANTHROPIC_API_KEY` (server-side, read by the function) and `VITE_SUPABASE_URL`, `VITE_SUPABASE_ANON_KEY` (build-time, baked into the client bundle by Vite) — same values as the local `.env`/`.env.local`, now living in Netlify's env store instead. Confirmed working via a live Kip round-trip against the deployed function post-deploy, not just a successful build.

**First deploy was manual (`netlify deploy --prod`), not git-linked, because the GitHub push needed the user's own credentials.** This environment couldn't authenticate `git push` (`fatal: could not read Username for 'https://github.com'`) — no cached credentials, no interactive terminal for GitHub's device/browser flow. Rather than block the whole phase on that, did a manual CLI deploy straight from the local `dist/` build to confirm the build genuinely works on Netlify's infrastructure (not just locally), then handed the `git push` step to the user. Continuous deployment (auto-rebuild on push) still needs linking in the Netlify dashboard once the push lands — that step requires authorizing Netlify's GitHub App, which is tied to the user's GitHub account and can't be done from a token alone.

**Domain purchase (`keepr.coach`) deferred to the user, by necessity.** It's a real financial transaction against their Netlify account's payment method — not something achievable via API token regardless of scope. Netlify sells domains directly through the dashboard; buying it that way auto-configures DNS (no manual record walkthrough needed), which simplifies what the original brief assumed would be a manual DNS step.

**Domain attached via the Netlify API, after confirming scope with the user first.** The account had two DNS zones — `keepr.coach` (this project, unattached, `site_id: null`) and a pre-existing, unrelated `beachhandball.live` zone tied to a different site. Explicitly confirmed with the user before touching anything, then used `updateSite` to set `custom_domain` and `configureDNSForSite` to create the actual DNS records — the zone existed from the purchase but had zero records until this ran. SSL provisioned automatically once the records existed.

**Continuous deployment: the API can configure the link, but can't grant real repo access — that gap cost one failed build.** Set the site's `repo` field via `updateSite` (provider, repo path, branch, build command), which looked complete in the API response, but the resulting auto-triggered build failed with `Host key verification failed` — Netlify had the repo *config* but no actual clone credentials (no GitHub App installed, no deploy key). That authorization step is unavoidably manual: it's a GitHub OAuth screen tied to the user's account. Once they completed it via the dashboard, triggered a fresh build via `createSiteBuild` and confirmed it built successfully with `commit_ref` matching the exact commit hash that was pushed — not just "the build succeeded" but "it pulled the real code."

## Post-launch — AI-writing content audit

**Audited landing page, Privacy Policy, and Terms copy against Wikipedia's "Signs of AI writing" checklist, at the user's request.** Two real findings, fixed: (1) overuse of em dashes as the default connector across all three files, now varied with periods, commas, colons, and parentheses depending on what each sentence actually needed; (2) a repeated "X, not Y" contrastive framing used five times on the landing page alone (headline, two feature-card titles, Kip's blurb, the dual-discipline line) — cut to two deliberate uses. Checked the full checklist against the files; found no hits on AI-vocabulary words (delve, crucial, tapestry, testament, vibrant, etc.), no promotional language, no copulative-avoidance ("serves as" instead of "is"), and no Title Case headers — those were already clean.

**"Outfield"/"outfielders" replaced with "court"/"court players" per the user's correction.** Handball doesn't use "outfield" — that's a cricket/baseball/soccer term; "court player" is the sport's actual term for a non-goalkeeper. Fixed the headline ("Not the court.") and the positioning strip.

**Local `netlify dev` hit an unrelated, unresolved quirk during verification — isolated, not chased.** Its HTML-transform step threw a parse error pinned to `index.html`'s `<title>` line, reproducing identically 3/3 times including after full cache clears and process kills, and persisting even after the flagged em dash was removed from that exact line — proof the reported location was misleading, not a real content issue. Verified the actual fix by running plain `vite dev` (no Netlify wrapper) instead, which rendered everything correctly with zero console errors. Since the deployed site builds via GitHub Actions independent of this local tool and Phase 6 already confirmed that pipeline works, didn't sink further time into Netlify Dev's internals for what's a local-only convenience layer.

## Warm-up, mental skills, and process goals

**Selective-attention and spatial-awareness exercises went into existing categories (Reflexes, Positioning), not a new one.** The brief asked these be "tagged clearly" as distinct from the existing cue-reading drills. The app has no tagging system beyond category/type/season, so rather than invent an 11th category for two exercises, placed them next to their closest existing sibling — *Noise-Filter Reaction Drill* in Reflexes (alongside *Colour-Call Reaction*, the existing divided-attention drill), *Multi-Target Tracking Drill* in Positioning (alongside *Six-Metre Line Reads*, the existing multi-player-read drill) — and made the distinction explicit in each description instead. Flagged for review; easy to split into a dedicated category later if it turns out two isn't enough to justify sharing space.

**The pre-session "focus" field lives inline on the Plans accordion row, not a new screen or step.** There was no existing "start a session" moment in the UI to hang a pre-session prompt on — sessions just sit there until marked complete. Added a lightweight single-line input directly on each uncompleted session's row (saves on blur, not per-keystroke, to avoid write-spam), surfaced back in `LogSessionModal` ("Your focus was...") and permanently on the completed-session summary. Also flagged for review — the alternative would have been a dedicated "start session" step, which felt like more structure than a one-line optional field warranted.

**Mental Side split preserved its original content rather than discarding it.** The old single entry's "reset routine" tip became the seed of the new "Resetting After a Goal" topic, reworded rather than duplicated, so the restructuring is additive-and-refined, not a content downgrade.

## App-inspired features

**Opponent record is best-effort, not guaranteed.** `result` is a freeform string ("24-19 W"), not structured win/loss data, and the brief explicitly ruled out adding new fields for this feature. `opponentRecord` only counts a match toward W/L/D if `result` ends in a standalone W/L/D letter — the form's own existing placeholder convention. Matches that don't parse still count toward the total-matches and save% figures, just not the record. Shown live while typing the opponent name in `MatchFormModal`, and on `MatchDetail`'s header.

**Added `session.completedAt`, one field, not covered by item 1's "no new fields" instruction (which was specific to opponent history).** RPE trend and the weekly streak both need to know *when* a session was completed, and nothing in the existing data model captures that — only `weekNumber`/`sessionNumber`, which have no relationship to calendar time. Sessions completed before this change has no `completedAt` and simply don't contribute to either feature going forward — old data doesn't retroactively gain a timestamp, it just doesn't count, which is the honest option (verified live: two sessions completed in earlier testing turns did not appear in the streak/trend until a session was completed under the new code).

**Weekly streak counts calendar weeks (Monday-start), and doesn't zero out mid-week.** If the current week has no completed session yet, the streak checks last week instead of breaking — the week isn't over, so nothing to punish yet. Matches the brief's explicit "no reset drama" instruction.

**"Due soonest" for the Today card is inferred, not scheduled.** Sessions have no real due date, only a position (week N, session N) within a plan that itself has `createdAt`. Approximated a due date as `createdAt + (weekNumber - 1) × 7 days` and picked the earliest incomplete one across *all* plans, not just the most recently created plan — closer to the literal "due soonest" wording than defaulting to "whichever plan is newest." Worth confirming this matches the intent if it ever produces a surprising pick with multiple concurrent plans.

**Video timestamp deep-links only work for YouTube.** The brief ruled out building real video hosting/playback for this version, so `videoLinkForShot` does the minimum useful thing: parse `mm:ss` / `h:mm:ss` into seconds, append `&t=Ns` for recognisable `youtube.com`/`youtu.be` URLs (the one host with a reliable, stable timestamp query param), and fall back to the plain video link for everything else (Drive, Vimeo, whatever) — the keeper just seeks manually there. No timestamp format validation beyond "does it parse" — matches whatever convention the keeper's video source already uses.

**Skill radar chart: proposed, not built.** Per the brief's explicit instruction not to guess silently on this one, proposed a formula (volume-per-category, normalized against the keeper's own max category, blended 50/50 with match save% only for the two categories — Diving & Ground Work, 1v1 & Breakaways — with a clean shot-type/zone mapping). On reflection with the user, the formula had a real conceptual problem, not just a presentation one: Keepr has no actual skill data, only training volume and (for 2/10 categories) match outcomes. Volume isn't skill — training a category a lot doesn't mean you're good at it, just that you've spent time on it. Calling that a "skill radar" oversold what the data can honestly support. Decision: skipped rather than built as either a relabeled "training emphasis" chart or a self-rating-based version — neither felt worth it right now. Revisit if either direction becomes worth it later; the volume/save% helper logic already lives in `rpeTrend`/`opponentRecord`'s neighborhood if resumed.

## Diagrams & fundamentals (sourced from a coaching book, rebuilt originally)

**Every diagram and every line of new copy was written/drawn fresh — no source reproduction.** The brief was explicit that the source (a 112-page GK fundamentals book) contributed only underlying *concepts*, not any content to copy or adapt. Treated that as a hard constraint: original SVG geometry computed from scratch (real angle-bisector math for the angle-narrowing diagram, not eyeballed), original wording throughout the new exercises and captions.

**Ball absorption became three separate linked exercises, not one entry with embedded progression notes.** The brief left this open ("your call"). Followed the app's own existing precedent: the sliding-technique progression (`Seated Slide Reach` → `Kneeling Slide Push-Off` → `Basic-Stance Slide Progression` → …) is already five separate entries that reference each other in prose, not one entry describing five stages. Matched that pattern for consistency and because it makes each tier independently filterable/schedulable in a plan, which one giant entry wouldn't be.

**Ball absorption exercises went into Core & Prevention, not Reflexes.** The brief flagged this as an open call. `Basic Catch Fundamentals` (already in Reflexes) is technique-focused too, so an argument existed either way — went with Core & Prevention because the brief's own framing centres the elbow-hyperextension injury risk as the reason this drill exists as its own thing, which matches that category's existing theme (Shoulder Stability, Anti-Rotation Core, Sliding Prep Mobility) more directly than Reflexes' reaction-speed focus.

**Cover-the-Frame Drill went into Positioning, not Reflexes.** Brief offered either. The skill being trained — resetting to cover the goal from wherever you land, under minimal-reset-time pressure — is fundamentally about positioning under time pressure, not raw hand speed, so it sits with `Six-Metre Line Reads` rather than the reflex drills.

**Warm-up entries were updated in place (`e50`, `e51` kept their ids), not replaced.** Deleting and re-adding under new ids would have silently orphaned the exercise reference in any existing plan session that already pointed at them (the app tolerates a missing exercise id gracefully — it just vanishes from the session's list — but there was no reason to risk it when renaming in place was just as easy). Two new phases (`e60` in-goal movement prep, `e61` distribution finish) were added fresh to complete the four-phase structure: general physical prep → in-goal movement prep → progressive throws → distribution finish.

**Diagrams built and shown one at a time before committing to the visual language, per the brief's explicit instruction not to guess.** Built the angle-narrowing diagram first, wired it into the real Advice hub (not a mockup), screenshotted it, and got sign-off on the approach — dashed lines for angle/sightlines, solid for the "correct" line, filled circles for shooter/keeper, small uppercase muted labels, existing token colors keeping their existing meanings (teal = correct/goal-line per the app's own design-token comment, red = danger/shooter, navy = structural) — before building the other three in the same language. The fourth diagram (straight-shot corner) introduced two new colors, WINTER blue and SUMMER orange, used only as a left/right path-and-corner pairing (not danger/correct semantics) since that diagram isn't a right-vs-wrong comparison like the other two-panel ones — reused existing tokens rather than inventing new colors, just for a different purpose than their usual court-season meaning.

## Structured reps/weight logging and progress graphs

**`prescription` renamed to a structured `reps` field set, with the original text always preserved verbatim.** Session-exercise entries now carry `repsRaw` (the exact original string, e.g. "4 x 6 each side" — never altered, so a parser bug can never corrupt what's displayed), plus best-effort `repsSets`/`repsValue`/`repsUnit`/`repsNote` parsed from it, and `repsWeight`/`weightUnit` for gym logging. `parseRepsFromFormat` handles the two dominant shapes in the library ("N x M unit" and "N reps/shots/throws"); anything it can't parse (e.g. "10 min flow", "3 reps per zone") just gets `sets`/`value`/`unit` left `null` — `repsDisplay(entry)` always falls back to `repsRaw`, so display is never affected by parser coverage gaps. Checked the actual exercise data before building rather than assuming: of 61 library exercises, the large majority parsed cleanly; 10 use an "each side"/"each leg" qualifier the base regex would otherwise have swallowed, which is why `repsNote` exists as its own field rather than being dropped.

**Gym-logging scope: every `type === "Gym"` exercise, weight optional — confirmed with the user rather than assumed.** Checked the actual data first: only 2 of 6 gym exercises have genuinely loadable weight (the rest are banded/bodyweight movements where "weight" doesn't really apply). Presented that finding plus three scope options via `AskUserQuestion` per the brief's explicit "ask me before building" instruction; user picked the broader "all Gym-type, weight optional" option over restricting to the 2 with real load. `GymSetLogger` therefore renders for any gym-type exercise in a session, and an empty/zero weight on a set is valid (bodyweight or banded work still gets reps-per-set tracked).

**`PlanEditor`'s template-editing UI was left as a single free-text input bound to `repsRaw`, not rebuilt into separate structured fields.** The brief's real new-UI ask was set-by-set logging at session-completion time (built), not editing a plan template's prescribed reps (pre-existing). Rebuilding that input into four structured fields would have been scope creep beyond what was asked, for a screen that isn't where the new value lives.

**Weight is hardcoded to kg, no unit toggle.** The brief allowed for `weightUnit`/lb but introducing a per-set or per-exercise unit toggle would complicate `loggedSets`' shape for a UK/European handball app where kg is already the assumed unit elsewhere. `weightUnit` stays as a field on the reps struct for future use if it's ever needed, but `GymSetLogger` and the "Logged: Xkg×Y" summary line both just assume kg.

## Data-driven goal-block generation

**Proposed the full weighting model before writing any generation logic, per the brief's explicit instruction, then built exactly what was confirmed.** Four real decisions were surfaced via `AskUserQuestion` rather than guessed: (1) a plateaued gym lift keeps the same exercise with a reason nudging more weight, rather than swapping to a "harder variant" — nothing in the library defines one, and inventing one would have been new-content scope creep; (2) added a `loadAreas` tag to all 61 library exercises so niggle exclusion is a deterministic hard rule instead of fuzzy text matching; (3) continuous weighted selection (a weak-zone exercise is more *likely*, not guaranteed a fixed slot count) over reserved data-driven slots; (4) sparse-data thresholds of ≥3 matches/≥15 shots this season for match stats, ≥4 completed sessions in the last 6 weeks for training logs. All four were accepted as recommended.

**`loadAreas` tags are my own judgment call from the same biomechanical read of each drill used for the exercise-description rewrite, not derived from any external source.** Controlled vocabulary: shoulder, elbow, wrist, hip, groin, hamstring, knee, ankle, low back, core, calf. Deliberately conservative — reaction/catching drills with no real joint stress got `[]`, diving/sliding/gym work got tagged to whatever the description's own movement genuinely loads.

**Niggle exclusion is a hard rule, not a soft deprioritization, matching Kip's existing "never suggest training through real pain" caution.** `excludedExerciseIdsForNiggles` treats a niggle as hard if severity is Significant *or* it simply hasn't been cleared by physio yet, regardless of severity — a Mild-but-uncleared niggle still excludes. The free-text `part` field is normalized against a small keyword dictionary (`NIGGLE_AREA_KEYWORDS`); if a hard niggle's text doesn't confidently match any known area, the fail-safe excludes every Gym and Core & Prevention exercise for that generation rather than guessing which ones are actually safe. A pool is never allowed to end up fully empty from exclusion alone — falls back to the unfiltered pool for that one category rather than producing a broken block.

**Zone/shot-type specificity is a small local lookup (`EXERCISE_ZONE_MAP`, `EXERCISE_SHOTTYPE_MAP`), not a persisted field, and deliberately covers only the handful of exercises that are genuinely zone-specific by their own description** (Near-Post Coverage Drill, Wing Shot Angle Reading, Low Ball Smother Drill, Spin Shot Anticipation, Beach Penalty (Spin) Reps). Everything else in Shot Reading/Diving & Ground Work/Positioning gets a smaller, generic category-level nudge with no reason text attached — only the genuinely-targeted picks get a reason, so the signal doesn't get diluted by claiming false precision for exercises that are actually zone-agnostic. This is a smaller-scoped implementation decision than the four asked up front, made in-flight rather than re-surfaced, since it doesn't touch the exclusion safety semantics and stays inside "only call out data-driven picks with real grounding."

**Training-log signal is attributed at the session level via majority category, using the same `createdAt + (weekNumber-1)*7` due-date inference `nextSuggestedSession` already uses**, since RPE and completion are logged per session, not per exercise. This is a real proxy, not a precise per-exercise read — flagged in the original proposal, accepted as the best available signal given the data model. Reduction (×0.6) triggers on completion rate under 50% or the last 3 RPE-logged sessions in a category averaging 8+, gated behind a ≥3-sessions-in-category sample size on top of the overall ≥4-completed-in-6-weeks eligibility bar, so one bad week doesn't skew a whole category.

**Verified against the real, unmodified generation code, not reimplemented test logic.** Since I couldn't safely exercise the "enough data" path against the live account without polluting real match/session history, extracted the pure-JS portion of `App.jsx` (everything before the first JSX component) into a standalone Node harness via `require`, then ran the actual `generateGoalBlock`/`excludedExerciseIdsForNiggles`/`categoryTrainingSignal` functions against synthetic data. Confirmed: `useData: false` and sparse-data `useData: true` both produce output indistinguishable from blind cycling (zero `genReason` anywhere); a clear weak zone produces the exact reason phrasing from the brief's own example; a Significant/uncleared niggle produces zero leakage of excluded exercises into a real generated block; unmatched niggle text triggers the Gym/Core & Prevention fail-safe; high-RPE and low-completion categories each correctly trigger the reduction; a flat 3-session lift history correctly triggers the plateau reason with no swap. The live `Builder` UI itself was also click-tested for the sparse-data path (toggle shows the honest "not enough data yet" message, generates a normal block with no errors when checked anyway).

## Kip alerts, points, and badges

**Proposed the three real judgment calls before building, per the brief's explicit instruction, then built exactly what was confirmed.** Point values (10/session, 15/match, 25/PR), the tier-4 badge scope (block completion only — "a full season of matches logged" has no natural number in the data model, so I didn't invent one), and LLM-phrased vs. templated alert delivery (LLM-phrased, matching the app's established "Kip reasons over structured data in natural language" pattern) were all surfaced via `AskUserQuestion` rather than guessed. All three were accepted as recommended.

**Points and badges are derived, computed fresh from existing data every time — not a mutable ledger.** `computeTotalPoints` and `computeEarnedBadgeIds` are pure functions over `plans`/`adHocSessions`/`matches`, exactly like `rpeTrend` or `weeklyStreak` already work in this codebase. This was a real architecture choice I made without asking (not one of the three surfaced questions) because it's strictly better than the alternative: a stored running total would need award-time mutation hooks wired into every completion/match/PR save path, with real risk of double-counting or drift if a session gets un-completed and re-completed. Deriving it fresh sidesteps all of that — there is nothing to get out of sync.

**"Don't repeat yourself" is fingerprint-based, not a time cooldown.** `computeKipAlerts` tags every currently-true condition with a fingerprint that only changes when the underlying situation genuinely changes — an escalating missed-session count, a new PR, a new calendar week — then filters out anything already in `profile.seenAlertFingerprints`. A condition that's still true but unchanged (e.g. the same plateaued lift, no new session logged) naturally doesn't re-fire; one that gets worse does, with fresh text. This means there's no arbitrary "alert every N days" timer to tune, and a condition that resolves itself (a missed-session run gets fixed by completing a session) simply stops appearing without needing explicit "resolved" handling.

**Threshold judgment calls I made without re-surfacing, since none of them touch the three confirmed decisions or carry the same stakes as the Storage RLS work:**
- Missed sessions: 2+ trailing incomplete sessions past their implied due date (same `createdAt + (weekNumber-1)*7` inference used elsewhere), walking backward from the end of a plan's session order.
- Weak zone/shot-type "genuine trend": splits the season's matches into older/newer halves, requires ≥4 matches total and ≥4 shots per zone per half, and a ≥15-percentage-point swing before calling it a real trend either direction — deliberately conservative so "your weakest zone" doesn't get relabeled as "getting worse" from noise.
- Streak at risk: nothing logged this week, Friday or later (weekday index ≥4, Monday-start), and `weeklyStreak` (which already ignores the current in-progress week) shows ≥1 — i.e., there's an actual streak to lose, not just an empty week.
- Niggle gone quiet: ≥10 days since the last rehab log entry, only for niggles not yet cleared by physio, and only once at least one entry exists — a niggle with zero log entries has no baseline date in the data to measure quietness from, so it's excluded rather than guessed at.

**Alert delivery reuses the exact same `callKip` request path as regular chat messages** (extracted as a shared helper from the pre-existing `sendMessage`), with a synthetic trigger `user` message that's sent to the API but never added to the visible message list — only Kip's reply gets appended, so the conversation reads as Kip genuinely opening with something rather than answering a visible prompt. The one real design point here: this triggers on every `KipChat` mount, but `computeKipAlerts`'s fingerprint filtering means it only actually calls the API when something is genuinely new — mounting with nothing new returns an empty array and the effect does nothing.

**A failed alert delivery fails silently and doesn't mark anything as seen** — verified live: with the local dev server unable to reach the Netlify function (plain `vite`, no function server), the request 404'd, the badge dot correctly stayed on the Kip tab, and nothing crashed. This is deliberate: a proactive nice-to-have shouldn't surface an error to the user, and leaving fingerprints unmarked means it correctly retries next time the conditions are still true.

**Alerts toggle lives directly in the Kip chat header** (a bell icon next to a new points readout), one tap from the badge that announces something's there — satisfies "not buried in a settings menu three taps deep" literally, and keeps it where the feature it controls actually lives rather than a general settings screen (there isn't one in this app).

**Points/badges display was a reasonable rounding-out, not explicitly requested but implied by "connective tissue."** The brief didn't ask for a dedicated points/badges screen, only that points exist and badges surface via alerts — but a running total with no way to ever glance at it felt incomplete. Added a small tap-to-open `BadgesModal` from the header's points readout, showing the three point-source counts and all four badges (earned highlighted, locked greyed out with their descriptions still visible) — restrained, matching the brief's explicit "not a game layer bolted on" framing, no progress bars or animations.

**Verification: full logic-layer coverage via the same Node-harness technique used for the data-driven-blocks feature, plus one real limitation flagged honestly.** Extracted the pure-JS portion of `App.jsx` fresh (line offsets shift as the file grows, so re-derived the cut point rather than reusing the old one) and ran 8 scenarios against the actual shipped functions: points totals, badge-earning at each tier, missed-session run detection, RPE-high consecutive detection (and correct non-firing when one session breaks the streak), fingerprint dedup (confirmed zero re-alerts once seen), fingerprint escalation (confirmed a fresh alert when a run gets worse), and readable text generation for all 12 alert types. Live-verified the badge indicator against the real account (a genuine condition was already true, dot appeared correctly) and the graceful-failure path. **Not verified live: the actual LLM-phrased combined message.** Local `netlify dev` reproduced the same unresolved local-only rendering quirk already documented earlier in this project (blank page, zero console errors) that a prior session decided wasn't worth chasing further given the deployed pipeline works independently of it — didn't re-litigate that call. The underlying request path (`callKip`) is identical code to regular Kip chat, already proven working in production many times over this build, so the risk here is low, but the specific alert-phrasing prompt genuinely hasn't been seen live yet. Worth a real check right after this deploys.

## Live Record feature (live training-session and match recording)

## Email infrastructure (ImprovMX) — production incident: a real data-loss race, and its fix

**Deploying and live-testing Phase C surfaced two real problems that only show up once code actually leaves this machine — worth recording precisely, not just the fixes.**

**Problem 1: the deployed function silently failed for a boring reason — the new environment variables never left my local `.env`.** `.env` is git-ignored (correctly), but that also means it never reaches Netlify's production environment on its own; syncing it there is a separate, explicit step this build hadn't done yet. `email-inbound.js` was live and reachable at its real URL the whole time, but `getSupabaseAdmin()` threw immediately on a missing `SUPABASE_SERVICE_ROLE_KEY`, was caught by the function's own error handling, and returned a quiet `200` — deliberately indistinguishable from "nothing to do here," which is correct behavior for hiding internal state from an unauthenticated caller, but also meant the failure was invisible from the outside. Confirmed via Netlify's own API (not assumed) that the function *was* deployed and *was* the right commit before looking anywhere else. Fixed by syncing the four env vars the code actually reads (`IMPROVMX_SMTP_USER`, `IMPROVMX_SMTP_PASS`, `SUPABASE_SERVICE_ROLE_KEY`, `VITE_IMPROVMX_DOMAIN`) to the live site — with the user's explicit confirmation first, since this is a production account-config change. Also found `IMPROVMX_API_KEY` sitting in `.env` unused (a leftover from the abandoned REST-sending approach) and `UNSUBSCRIBE_SECRET` not yet referenced anywhere (Phase E hasn't built the unsubscribe link yet) — deliberately did not sync either, since pushing an unused secret to production has no benefit and one more thing to accidentally leak.

**Along the way, live testing also proved the IP allowlist (from the Phase C entry above) was actively hazardous, not just unproven — a direct curl POST from an unrelated IP was correctly rejected, which is exactly what would happen to a genuine ImprovMX delivery if their real sending IP ever differs from the one address found in their public docs, with no way from here to see Netlify's function logs and confirm either way.** Downgraded the check from a hard reject to a logged warning — full reasoning already captured in the Phase C entry above; noted here because this fix and the one below were pushed together.

**Problem 2, the real one: a genuine data-loss bug, not a testing artifact.** While stress-testing the live pipeline with several forwarded-email requests in quick succession, `profile.inboundAlias`, `profile.alertsEnabled`, and `profile.emailAlertCategories` were found wiped from the real dev account in Supabase — reset to nothing — even though the browser's own in-memory copy of that same profile stayed correct the entire time. Root cause: `email-inbound.js`'s write was a **read-then-write of the entire `data` JSONB blob** — fetch the full row, spread it in JavaScript, append one item to `pendingCalendarSuggestions`, write the whole thing back — to append a single array entry. Two overlapping invocations for the same account (exactly what happens if a keeper forwards more than one email close together, and trivial to trigger by firing test requests back-to-back) race on that pattern: each reads a snapshot, and whichever write lands second silently reverts everything the first one changed, including fields the second invocation never touched or even knew existed. This is the same *category* of bug as the `addReportAndNotify` stale-closure fix earlier in this build, but one level lower and more dangerous — that one was a same-process JavaScript closure race, fixable by combining two calls into one `updateAndSave`; this one is a genuine **cross-invocation database race**, which no amount of restructuring the JavaScript call sites can fix, because the two invocations are two separate Lambda-style executions with no shared memory to synchronize through.

**Fix: `supabase/migrations/0003_atomic_pending_calendar_suggestion.sql` adds a Postgres function, `append_pending_calendar_suggestion(user_id, suggestion)`, that does the append as a single atomic `UPDATE ... SET data = jsonb_set(...)` statement — no read step in application code at all.** Postgres's own row-level locking makes concurrent calls to this function serialize correctly by construction; there is no window for one invocation's write to be based on a snapshot that predates another's. `email-inbound.js` now calls this via `.rpc()` (through a new `appendPendingCalendarSuggestion` helper in `supabaseAdmin.js`) instead of `saveUserRowById` with a hand-assembled full blob. The function is granted to `service_role` only, revoked from `public` — it takes an arbitrary `user_id`, so exposing it to the anon/authenticated roles would let one account write into another's row. Migrations in this project are run manually via the Supabase dashboard's SQL Editor (established pattern from `0001`/`0002`) — asked the user to run it directly rather than attempting to execute DDL through the service-role REST client, which only calls existing functions and has no privilege to create new ones.

**Verified the fix actually closes the race, not just that it compiles.** After the user ran the migration, called the new RPC directly first (confirmed `profile.inboundAlias` and every other profile field survived a single append untouched), then fired **eight genuinely concurrent calls** (`Promise.all`, no sequencing) against the same account — deliberately reproducing the exact overlapping-invocation shape that caused the original data loss, amplified well past what a keeper forwarding two emails close together would ever produce. All eight suggestions landed, the one already present survived, and `profile.inboundAlias` came through completely intact. Test data was removed afterward by clearing `pendingCalendarSuggestions` back to empty, and the account's genuinely-lost fields (`inboundAlias`, `alertsEnabled`, `emailAlertCategories`) were restored by triggering one fresh save from the browser, which still held the correct values in memory the whole time — no data was permanently unrecoverable, since the corruption only ever touched the database copy, not the live client's own state.

**Takeaway for anything built the rest of this project: any server-side JSONB mutation on `user_data` that isn't a full, single-writer, user-initiated save (the normal client `updateAndSave` path, which only ever has one writer — the signed-in keeper's own browser) needs to go through an atomic SQL function like this one, not a fetch-then-write.** The scheduled alerts job in Phase E will write to this same table from a different server-side code path and needs the same discipline applied from the start, not discovered the same way this one was.

**After fixing the race condition, a real forwarded email through the live ImprovMX pipeline still produced nothing — with ImprovMX's own delivery logs confirming a successful `200` from the webhook, which made this the most confusing failure of the whole build.** Every layer had already been independently verified: the function was deployed (confirmed via Netlify's API), the atomic RPC worked (confirmed with a genuine 8-way concurrent-call stress test), and ImprovMX's own Logs tab showed `DELIVERED — Delivered via webhook` to the exact right URL. ## Email infrastructure (ImprovMX) — Phase D: season schedule bulk upload

**The brief asks for three input formats — PDF, spreadsheet, or a photo — but Claude's document/vision API only natively reads PDF and images, not `.xlsx`/`.csv`.** Rather than silently narrowing scope to "PDF and photo only," this was raised directly: add a spreadsheet-parsing dependency and genuinely support all three, or ship without native spreadsheet support and have a keeper export to PDF first. Confirmed: build full support for all three.

**The first spreadsheet library installed (`xlsx`/SheetJS 0.18.5) had two unfixed HIGH-severity advisories — prototype pollution and ReDoS, both triggerable by the exact thing this feature does: parsing a file a keeper uploads.** `npm audit` surfaced this immediately after install, before any code was written against it. Removed it and installed `exceljs` instead, which does carry one moderate transitive advisory (via `uuid`, only reachable if the caller passes a custom pre-allocated buffer to `uuid.v3/v5/v6` — not how `exceljs` invokes it internally, and not something this code's own usage touches), a materially different risk profile from two high-severity, directly-file-content-triggerable, no-fix-available issues in code whose entire job is parsing untrusted uploads. `exceljs` handles genuine `.xlsx` binary parsing (an OOXML/zip format, not reasonable to hand-roll — unlike the plain-text `.ics` parser elsewhere in this build); `.csv` needs no library at all, since it's already the plain text format Claude reads.

**`ScheduleReviewModal` is the bulk sibling of `PendingCalendarReviewModal` from Phase C — same "never commit silently" discipline, but the brief's explicit requirement here is different: "let the keeper deselect any that got misread rather than accept-all-or-reject-all."** Every extracted fixture starts checked and editable (opponent, date, competition), individually togglable, with the confirm button's own label ("Add N matches") tracking the live selected count rather than a fixed all-or-nothing action. The uploaded file itself is never persisted to storage — unlike a PT/physio plan, there's no reason to keep a season schedule file around once its fixtures have been reviewed and added, so it's read directly in the browser and discarded. ## Email infrastructure (ImprovMX) — Phase E: scheduled Kip email alerts

**Reuses `computeKipAlerts`, `describeAlertItem`, and `buildKipSystemPrompt` exactly as the in-app alerts feature already does — no separate email-specific condition logic exists anywhere.** The only genuinely new piece of *detection* logic is the category/cooldown filter layered on top of whatever `computeKipAlerts` already returned, which is a filter, not a reimplementation. This is the payoff for moving `DEFAULT_EXERCISES` into `kipDomain.js` alongside the rest of the domain layer this turn (same reasoning as the Phase A extraction, one level further): `computeKipAlerts`'s plateau/PR alerts need real exercise *names* for their descriptions, and the scheduled function has no browser-loaded copy of the curated library to draw on — only whatever's in each account's own `customExercises`. Verified this was a real gap (not a hypothetical one) before moving anything: confirmed the file is pure data, no JSX or icon references, safe to relocate exactly like the earlier domain-logic move, and confirmed via a clean rebuild plus a live browser check that the Library tab's 55 stock exercises still render identically afterward.

**Netlify Scheduled Functions have a real, documented 30-second execution limit** — confirmed via Netlify's own coding-context tool rather than assumed, since guessing wrong here would mean silently-truncated alert runs discovered only in production. `scheduled-alerts.js` processes every account concurrently (`Promise.allSettled`, not a sequential loop) so one slow account's Kip call can't crowd out the rest of a run within that window. This is a real scaling ceiling worth being explicit about, not a hidden one: at Keepr's current real scale it's a non-issue, but if the user base grows substantially, this function would need to move to a Netlify Background Function (15-minute limit, but no built-in schedule trigger of its own — would need something else to invoke it on a timer) or be sharded across multiple scheduled runs. Documented here rather than silently designed around, since the trade-off is real and worth someone's deliberate decision if it's ever actually hit.

**Per-fingerprint cooldown (4 days) sits on top of `computeKipAlerts`'s own fingerprint scheme rather than inventing a second one.** A condition's fingerprint already changes when the underlying data genuinely changes (e.g. `missed:${planId}:${count}` — a keeper missing a 3rd session produces a different fingerprint than missing a 2nd), so "resolution" is handled for free by the existing fingerprint design; the cooldown's only job is stopping the *same* still-true fingerprint from re-emailing every single day for something that hasn't changed. `profile.emailAlertLog` (a new field, `{fingerprint, sentAt}[]`) is checked, not the in-app `seenAlertFingerprints` — the two surfaces track "has this been shown" independently on purpose, so opening the in-app Kip tab doesn't silently suppress an email that was never actually seen, and vice versa.

**Per-category preferences (built in Phase B, unused until now) finally get consumed here — `categoryForAlertType` filters each account's eligible alert items against `profile.emailAlertCategories` before anything reaches the cooldown check or a Kip call**, so a keeper who's turned off "Gym plateaus" in Profile never gets a plateau condition counted toward *anything* in that day's email, not just excluded from the final text.

**Live Kip call, per the earlier `AskUserQuestion` decision — one email per account per run covering everything newly-eligible, not one email per alert type**, structurally identical to the alerts/reports "compute then narrate" shape already established twice elsewhere in this build (plain prompt, no tool-calling, explicit instruction not to write it as a bulleted list). Cost is bounded by construction: a live Anthropic call only happens for an account that actually has something new and category-permitted to say, never for every account on every run.

**Unsubscribe is a stateless, signed link (`netlify/lib/unsubscribeToken.js`) — an HMAC of the user id using a secret Anthropic key never sees, verified with `timingSafeEqual`** — deliberately no unsubscribe-token table, since the whole point of the link is working for a recipient who isn't logged in (there's no session to check against). It flips the exact same `profile.alertsEnabled` flag the in-app toggle and Profile's "Email alerts" card already write to, not a second independent switch — turning alerts off from the unsubscribe link, the in-app toggle, or Profile all converge on one piece of state. `netlify/functions/unsubscribe.js` is intentionally public and unauthenticated (reached by clicking a link in an inbox, not by being signed in) and returns a plain, self-contained confirmation page rather than routing back into the app.

**Both new server-side writes (`append_email_alert_log`, `set_alerts_enabled`) went through the same atomic-SQL-function discipline established in migration 0003 from the start this time, not discovered the hard way a second time.** Migration `0004_email_alert_atomics.sql` adds both as `security definer` functions granted only to `service_role`. Verified concurrency safety directly with the same technique as the 0003 incident: three genuinely concurrent `appendEmailAlertLog` calls against the same account, confirming all three landed and unrelated profile fields (`inboundAlias`) survived untouched.

**Verified with real sends, not synthetic assertions, wherever a real trigger existed to test against.** The real dev account currently has zero live alert conditions (nothing to responsibly test the send path against without fabricating one), so `processUser` was temporarily exported, called directly with a synthetic-but-realistic quiet-niggle condition (a niggle with an uncleared rehab log 14 days old — `niggleQuietSignals`' own real threshold, not a mocked function), and reverted to module-private again immediately after — the shipped file is unchanged from what ships, only briefly more visible for the duration of one test. That real run generated a real Kip email, sent it via the real SMTP path (with explicit permission asked first, same as every other real send this session), and correctly appended `niggle_quiet:test-niggle-1:2` to the account's `emailAlertLog` — confirmed present, then removed afterward. The unsubscribe endpoint was verified with both an invalid token (correctly rejected, 400, no mutation) and a genuinely valid one (correctly flipped `alertsEnabled` to `false`, left every other profile field — including `inboundAlias` — untouched, confirmed, then restored to `true` to leave the real account in its original state). The cooldown filter itself was unit-tested against three cases (just-sent, never-sent, and a 10-day-old entry against a 4-day window) with the exact same function body the shipped code uses, not a paraphrase of the logic.

## Teammate connections & share with coach — Part 1: the permission model

**This is the first feature in the whole build where an authenticated client — not server-side service-role code — legitimately needs to write into another user's `user_data` row.** Every prior cross-account touch (inbound email, scheduled alerts, unsubscribe) went through `supabaseAdmin.js`'s service-role client, invoked by trusted server code with no signed-in user to scope to. Migration 0001's RLS has exactly one rule (`auth.uid() = user_id`, no exceptions) and was never meant to bend for this. Per the brief's explicit instruction, this was proposed and confirmed *before* any RLS policy or cross-account write path was written — three `AskUserQuestion` decisions, all confirmed on the recommended option: an invite-code/link connect mechanism (not email lookup, which needs its own account-enumeration-safe endpoint; not username search, which needs inventing a username system that doesn't exist and is closest to the "discoverable search" the brief explicitly rules out); recording permission as its own explicit, per-direction, independently-revocable grant, separate from the connection itself (connecting establishes mutual visibility, nothing more — it does not imply "you may write data into my account," which is a materially bigger grant than accepting a teammate request would normally suggest); and a keeper-chosen weekly/monthly cadence for Part 2's coach digest.

**Schema (`0005_teammate_connections.sql`): two new tables, `keeper_invite_codes` and `connections`, both RLS-enabled with only a `SELECT ... auth.uid() = ...` policy — no INSERT/UPDATE policy for `authenticated` on either.** Every mutation is a `security definer` function. This is the same mechanism migrations 0003/0004 used, but a meaningfully different trust shape: those functions are granted only to `service_role` and take a caller-supplied `user_id` because there's no session to read one from. These functions are granted to `authenticated` and **never** trust a caller-supplied identity — every one of them reads `auth.uid()` itself, and every one that touches another account's data (`create_or_resume_teammate_match`, `patch_teammate_match`, `delete_teammate_match`) re-runs `can_record_for(auth.uid(), p_owner_id)` on that exact call, not once at match-start. Verified this actually matters, not just in theory: revoking mid-session and immediately attempting another write was the single most important test in the whole verification pass, and it failed correctly (`Not permitted to record for this account`), with the owner's already-written data provably untouched by the blocked write.

**`can_record_for` reads two independent boolean columns on the connection row — `requester_allows_recipient_to_record` / `recipient_allows_requester_to_record` — not a single shared flag.** Each keeper flips only their own outgoing column (`set_recording_permission` figures out which one based on which side of the row the caller is on); accepting a connection request never touches either. Invite codes are never a browsable table — `keeper_invite_codes` has a SELECT policy for your own row only, and code→owner resolution happens exclusively inside `redeem_invite_code`, so there's no way to enumerate anyone else's code even accidentally.

**Matches stay two separate records, exactly as specified — no joint/shared-match concept was built.** `create_or_resume_teammate_match` creates an ordinary Match object (same shape `MatchFormModal` already produces) inside the *owner's* `matches` array, tagged `recordedBy`/`recordedByEmail`. Recording a shot (`patch_teammate_match`) is a generic jsonb merge-patch onto that one match — deliberately shaped to mirror the client's own existing `onUpdatePatch({...}) => saveMatch({...match, ...patch})` pattern, so `LiveMatchRecorder` needed zero new shot-logging/pause/finish logic. It just derives `activeMatch` from a `activeRecorder` ("self"/"teammate") toggle and points the exact same `logShot`/`removeShot`/`finish` handlers at either the local `onUpdatePatch` prop or the new RPC.

**"The keeper being recorded for can review and correct their portion afterward" needed no new editing UI at all.** Once a teammate-recorded match exists in the owner's own row, it's indistinguishable from any other match under RLS — the owner's completely ordinary, pre-existing `MatchDetail` edit/delete-shot controls are the correction mechanism, going through their own normal `auth.uid() = user_id` path with no RPC involved. A small `UserPlus`-badged "Recorded by {email} — edit anything below to correct it" label (MatchDetail and the Stats match list) is the only UI addition, there to make the review affordance discoverable, not to enable it.

**A deliberate v1 scope cut, documented rather than silently accepted: teammate-recording mode does not survive a page reload.** The base recording feature's crash-resilience (`findActiveRecording` scanning for any `recording` field left set) only ever looks at the current user's own loaded blob — it has no way to know "was I also recording for a teammate" after a reload, since that's session-local React state (`activeRecorder`, `teammateMatch`), not persisted anywhere. If Tom's tab closes mid-match, his own match resumes normally; any shots already logged into the teammate's account are safe (each was its own atomic write), but he'd need to re-select the teammate from a fresh "Start a live match" flow to keep going — `create_or_resume_teammate_match`'s same-fixture lookup means this doesn't create a duplicate, just requires the manual step. Considered building full cross-account resume detection and cut it: the brief's actual requirements (mutual consent, revocable, no retroactive effect, review-and-correct) don't depend on it, and it would have meant either exposing a cross-account read RPC beyond what's needed or duplicating `findActiveRecording`'s logic server-side for a genuinely rare edge case (a live match recorder backgrounded hard enough to reload, specifically while in teammate mode).

**Verified against two real, confirmed Supabase test accounts (service-role `admin.createUser`, `email_confirm: true`, deleted at the end — FK cascades on `auth.users` clean up their `connections`/`keeper_invite_codes`/`user_data` rows automatically), driving the exact RPCs the client calls, not a mocked approximation:** self-redeem correctly rejected; re-redeeming the same code is idempotent (returns the existing pending row, doesn't spam duplicates); accept flow; recording blocked before permission is granted; granted; a teammate match created with the correct `recordedBy`/`recordedByEmail`; re-triggering "start" for the same fixture resumes rather than duplicates; shots patched and visible; the owner reading their own row via their own authenticated client (not service-role) sees the teammate's shots and correct attribution; the owner correcting it afterward via a plain, ordinary `user_data` update under their own RLS — no RPC involved, confirming the "no new editing UI" design actually holds; revoke; and the very next write blocked immediately afterward with the owner's prior data provably unchanged.

## Teammate connections & share with coach — Part 2: share with coach

**Needed zero RLS changes and no new cross-account write path at all — the entire feature lives inside the keeper's own `profile` object** (`coachEmail`, `coachShareCategories`, `coachDigestCadence`, `lastCoachDigestSentAt`), the same trust boundary every other Profile setting already sits inside. This is the direct payoff of scoping Part 1's hard problem correctly: a coach's email address is just data the keeper owns, not a second account requiring its own consent flow — confirmed explicitly out of scope by the brief ("no coach-side login or dashboard").

**Reused, not reimplemented, per the brief's explicit instruction: `computeReportData` (the exact function the in-app "Generate report" button already calls) moved verbatim into `kipDomain.js`** — it had zero App.jsx-specific dependencies (no `callKip`, no React, no JSX) once inspected, making it a clean pure move exactly like `DEFAULT_EXERCISES` and `computeKipAlerts` before it. `computeCoachReportData` wraps it rather than duplicating it: filters the output by the keeper's three category toggles (training logs / match stats / attendance — default all on, only when a coach email is first added) and adds an `attendance` list `computeReportData` never needed for the keeper's own all-time report. Outbound sending reuses `sendOutboundEmail` (the same ImprovMX SMTP path built for Kip's alert emails) with zero new email infrastructure.

**One departure from a literal "reuse the report structure" reading, made deliberately: a coach digest is windowed to the reporting period (since the last digest, or one cadence period back if none has been sent), not all-time like the keeper's own on-demand report.** A weekly digest repeating a keeper's entire career history every single send would be exactly the kind of noise the brief's "no bulk/marketing email" spirit warns against, even though it's transactional. `sentToCoach: true`-tagged reports are still appended to the keeper's own `reports` array afterward (same shape, extra fields), so what a coach received stays visible and reviewable in-app — "what did my coach actually see," not a black box.

**One weekly scheduled function (`coach-digest.js`, `@weekly`) serves both cadence choices — no second scheduled function for "monthly."** `coachDigestDue` compares each account's own `lastCoachDigestSentAt` against its own chosen cadence (7 or 30 days); a monthly keeper is simply not due on three out of every four weekly runs. `send-coach-digest-now.js` (Profile's "Send now" button) shares the exact same `sendCoachDigestForUser` implementation, authenticated the same bearer-token way as `kip-chat.js` (verifies the caller's own JWT, operates only on their own account — no arbitrary user_id, unlike the scheduled path's service-role access). `callKipDirect` — previously duplicated verbatim inside `scheduled-alerts.js` — was extracted to `netlify/lib/callKipDirect.js` once a second caller needed the identical fetch/error-handling logic, rather than letting a third copy exist.

**Both new server-side writes (`append_report`, `set_last_coach_digest_sent`) went through the same atomic `security definer`, `service_role`-only discipline as every prior server-side mutation in this build** (migration `0006_coach_digest_atomics.sql`) — no exceptions taken even though this feature's own new RPCs (Part 1's) are the first ones ever granted to `authenticated`; these two specifically take an arbitrary `user_id` and are only ever called from trusted server code, so they stay service-role-only like 0003/0004.

**Verified with a real end-to-end send, not a synthetic assertion: a temporary confirmed test account, seeded with genuinely realistic plan/ad-hoc/match data, with `coachEmail` pointed at a real inbox.** `coachDigestDue` correctly `true` before any send (never sent), the real send succeeded (Kip generation, SMTP delivery, `append_report`, `set_last_coach_digest_sent` all landing), and `coachDigestDue` correctly flipped to `false` immediately afterward. One real bug caught by this test and root-caused before being written off as a false alarm: the delivered email said "no match shots logged," which first looked like a windowing defect — turned out to be the test script's own synthetic shot data using invalid zone codes (`z1`/`z2`/`z3` instead of the real `TL`/`TM`/.../`BR` keys), silently dropped by `aggregateMatchStats`'s `if (!z) return`. Re-verified `computeCoachReportData` locally (no real API/email cost) with correct zone codes and confirmed both the aggregation (67% save rate, correct weakest zones) and the date-window filtering (an out-of-window match correctly excluded, an in-window one correctly counted) are right — the shipped computation was never actually wrong, only the disposable test fixture was.
